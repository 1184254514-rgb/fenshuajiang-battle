## 两个独立维度

| 字段 | 允许值 | 含义 |
|---|---|---|
| 实现状态 | 未实现 / 部分实现 / 已实现待对照 / 已验收 | 记录实现和对照验收的进度 |
| 证据分类 | 已有原版证据 / 本地适配 / 证据不足 | 记录具体结论的依据性质，不随测试通过自动变化 |

已有原版代码支持某个条件，不代表系统已完整还原。一个任务涉及多类证据时，正文逐结论记录，必要时拆单；看板分类表示任务主要结论，不能掩盖缺口。Issue 正文、`实现:*` / `证据:*` 标签与 Project 同名字段保持一致。

流程阶段另外记录为待办、进行中、待验收、已验收；它不取代上述维度。Issue 保持 open 直到本项满足验收标准。提交、PR 合并或 Release 发布只关联交付，不能自动认定通过验收。

## 每轮必须执行

1. 开工前读取 AGENTS、差异清单、既有核对记录、当前源码与远端，保留未提交开发工作。选择一个具体 Issue，写清差异、原版依据、可观察的验收标准和本轮边界；大类任务拆出独立子项。
2. 开发中在同一任务追加确认规则、证据冲突、缺资源及本地适配；记录录像来源/版本/时间点或包摘要/文件/函数地址/配置项及其支持范围。证据不足时保留行为并注明，继续有依据的独立工作。
3. 提交时使用 `Refs #编号` 关联，更新 Issue 评论和差异清单。附实际源码 SHA、测试命令及结果、EXE 操作、完整日志检查、截图/录屏、Release 和校验值；注明测试注入，未执行的验证明确写未执行。
4. 自测完成后更新 Issue 标签和 Project：流程为待验收、实现为已实现待对照。原版同条件对照满足标准后，记录验收人/日期/依据/操作条件/结论，才设已验收并关闭任务；发现回归则重新打开并降回实际状态。

原版一致性按运行录像与操作结果、原包代码/资源、配置表排序。用户固定改动（四分钟、不同颜色、自交回退、底部技能入口、隐藏 F8）与明示本地适配按其指定标准验收，证据仍保留“本地适配”。离线适配验收不表示恢复官方服务。

## 看板维护与权限

仓库 Issue 表单、PR 模板负责收集信息，不会自动把正文下拉选项写入 Project 字段。每轮由执行开发的 AI 实际同步并核对；标签用于 Issues 侧独立筛选。不要把默认 Done 或“关闭任务”自动化当作原版验收。

当前 Git 凭据可写仓库和 Issues，但缺少 Projects API scope；创建项目使用已登录网页，不增加凭据权限。后续可继续通过网页更新；若网页或 API 不可用，保留 Issue 内完整记录，如实说明未同步字段，恢复后补齐。不得声称未验证的远端操作已经成功。
